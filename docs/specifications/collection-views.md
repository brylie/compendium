# Collection views: Table, Board, Calendar

**Depends on:** [`data-model.md`](./data-model.md) §2 (Collections and views), [`internal-links.md`](./internal-links.md) §1 (`referencedRecordId` resolution), [`service-layer.md`](./service-layer.md)

---

## 1. Scope

This covers the shared view-projection model, the `collection_view` Document block Table/Board/Calendar render through (issue #9), and the "smallest shared view configuration" (`EmbeddedViewConfig`) they needed — a deliberately minimal slice of #32's fuller ambition; see §6 for what's still open there. It does **not** cover saved-view persistence beyond what's described in §4, saved/reusable view _presets_ independent of a specific block, or aggregations/charts/dashboards (#10).

**"View" always means a Collection/database view here** — Table, Board, Calendar, and future renderers over one Collection's records — never an MVC-style page or route. There is no standalone view route. A View exists only as `viewConfig` on a `collection_view` block: a Document block, embedded inline like any other (a paragraph, a `page_link`), not a page of its own. The one pre-existing exception is `/table/[id]`, a full-page Table route for a Collection that predates this feature and is unrelated to it — it stays as-is.

## 2. `collection_view`: a Document block, not a route

A `collection_view` block is a `WorkspaceRecord` whose `parentId` is a Document, like any other block, with two extra fields (`data-model.md` §1/§2):

- `referencedRecordId` — the target Collection's ID, the same field `page_link`/`synced_block` use for "what this block references." Resolved and permission-checked the same way `page_link`'s target is (`internal-links.md` §1) — see §5 below for the MCP-facing specifics.
- `viewConfig: EmbeddedViewConfig` — `{ viewType: 'table' | 'board' | 'calendar', filters?, sort?, visibleProperties?, groupBy? }`. `filters` is an array of `{ propertyKey, op: 'is' | 'is_not' | 'is_empty' | 'is_not_empty', value? }`, ANDed together. `sort` is `{ mode: 'manual' | 'property', propertyKey?, direction? }` — `'manual'` leaves record order as-is (Board additionally layers a session-local per-column drag order on top, see §3). `visibleProperties` is a property-key allowlist; omitted means "all visible." `groupBy` is the one property driving the layout — a `select` property for Board's columns, a `date` property for Calendar's placement (Table doesn't use it).

Both fields are written directly to Yjs from the UI (`setRecordReferencedId`/`setRecordViewConfig` in `src/lib/data/records.ts`), the same direct-mutation pattern every other block edit uses — not routed through the service layer (`service-layer.md`'s contract is for MCP/route-handler writes; this is human UI editing, audited generically per `audit-coverage.md`, same as a Table schema edit).

**Inserting one:** the slash menu's "Collection view" command (`SlashMenu.svelte`) converts the current block to `collection_view` with no target set. `CollectionViewBlock.svelte` then renders an inline picker — a view-type select and a Collection select, mirroring `page_link`'s unlinked-picker state (`internal-links.md` §2) — and writes both `referencedRecordId` and `viewConfig` together once the user picks both and clicks Insert. A "Change" button on a configured embed reopens the same picker to retarget it.

**Two embeds, one Collection:** two `collection_view` blocks referencing the same Collection with different `viewConfig` are independent — each is its own `WorkspaceRecord` with its own `viewConfig`, so filtering one doesn't affect the other, and both read/write the same underlying records live.

## 3. The shared projection: `src/lib/data/views.ts`

A Collection stays the sole structured-data source of truth (`data-model.md` §2): this module only ever reads `WorkspaceRecord[]`/`PropertyDefinition[]` already loaded from Yjs and returns derived arrays. Nothing here mutates a record, copies one, or adds a view-specific field. `ViewConfig`/`ViewFilter`/`ViewSort`/`EmbeddedViewConfig` are defined in `src/lib/data/types.ts` (re-exported from `views.ts` for existing import sites) — `types.ts` is where `WorkspaceRecord.viewConfig`'s type needs to live regardless, so the view-config shape and the block-storage shape share one definition rather than two that could drift.

- `getCollectionView(doc, collectionId)` — the one Collection query/projection path. `TableCollectionView`/`BoardCollectionView`/`CalendarCollectionView`/`/table/[id]` all call this, so a record edit shows up identically in whichever view is open — there's no separate per-view data path to fall out of sync.
- `applyFilters` / `applySort` / `projectRecords` — pure functions composing filters/sort over a records array.
- `visibleProperties(schema, config)` — the schema filtered down to `config.visibleProperties`, or the full schema when unset.
- `groupBySelectProperty(records, property)` — Board's column grouping. Returns one `BoardColumn` per schema-defined option, **in schema order, even when empty** (data-model.md's "preserve empty groups… do not create placeholder records" — an empty column is a rendering fact about the schema, not a record), plus a trailing catch-all column for records with no value (or an option ID no longer in the schema).
- `dateKeyForRecord(record, property)` — the `YYYY-MM-DD` portion of a `date` property's value, or `undefined` if unset. Calendar buckets records by this key; records where it's `undefined` render in an "Unscheduled" list rather than being silently dropped.

This is the entire "smallest shared configuration" issue #9 asked for — it is not `query_collection`'s eventual filter/sort implementation (see §6).

## 4. The three renderers

Each is a standalone component (`src/lib/components/*CollectionView.svelte`) taking `{ collectionId, config: ViewConfig, onConfigChange }` — no route, no page chrome, no knowledge of being embedded. `CollectionViewBlock.svelte` is the only thing that knows about `collection_view` blocks: it resolves `referencedRecordId`, renders the picker/broken/resolved states, and wires `onConfigChange` to `setRecordViewConfig` so a config edit persists straight to the embedding block. This is why `config` is passed as a plain prop with a callback rather than Svelte's `bind:` two-way binding — the value's source of truth is a Yjs record read on every render, not component-local state.

**Table** (`TableCollectionView.svelte`) — a grid over `visibleProperties(schema, config)` columns and `projectRecords(rows, config)` rows, each cell a `PropertyValueCell.svelte` (the same property-type-to-editor mapping every view shares — text/number/date/select/checkbox/relation, one implementation, not reimplemented per view). No inline schema editor; a small link points to `/table/[id]` for adding/removing property columns, since that full page already owns schema management.

**Board** (`BoardCollectionView.svelte`) — `config.groupBy` names the `select` property driving columns; a dropdown lets the user switch it if the schema has more than one, or the collection gets prompted to add one (`updateCollectionSchema`) if it has none, rather than silently rendering nothing. Cards show the record's first `text`-type property as a directly-editable title, plus whatever other schema properties are in `visibleProperties`. Moving a card between columns — via native HTML5 drag-and-drop, a card's own "Move to" `<select>` (a keyboard/screen-reader-accessible alternative to drag-and-drop), or the card's own field editor if the grouping property is also a visible field — updates that record's existing grouping property (`updateRecordProperties`); it is never a reorder of Collection membership or a record copy. Manual sort mode (`config.sort.mode === 'manual'`, the default) additionally supports dragging a card to a specific position within a column — that ordering is **session-local component state** (`manualOrder: Record<columnKey, recordId[]>`), not written to the block or the Collection (see §6 for why manual order specifically stays ephemeral even though the rest of `viewConfig` now persists).

**Calendar** (`CalendarCollectionView.svelte`) — `config.groupBy` names the `date` property driving placement, same add-one-if-missing prompt as Board. A fixed 6-row/42-cell month grid (leading/trailing days from adjacent months included, so the grid's shape doesn't jump between 5- and 6-row months) places each record on the day matching `dateKeyForRecord`; a record with no value for the date property renders in an "Unscheduled" section below rather than being hidden. Every entry (scheduled or unscheduled) renders its date property inline via `PropertyValueCell`, so rescheduling — including giving an unscheduled record its first date — is a direct edit. A day cell's "+" button creates a record with that day pre-filled (`createRecord`).

## 5. Permission scoping and `get_document`

`services/documents.ts`'s `getDocument` treats a `collection_view` block's `referencedRecordId` exactly like a `page_link`'s (§ referenced in `internal-links.md` §1): `tokenAllowsParent` is already parent-kind-agnostic (checks a token's `allowedDocumentIds` _or_ `allowedCollectionIds`), so an out-of-scope target is omitted from the response — never leaking the target Collection's title or schema to a caller who was never granted access to it — using the identical `targetInScope` computation `page_link` already had. `viewConfig` is included only once `referencedRecordId` resolves to an in-scope Collection — omitted both when the target is out of scope (it can name properties from a schema the caller isn't scoped to see) and whenever the block is broken (target deleted, or resolves to a Document rather than a Collection), not just the out-of-scope case. `referencedRecordId` itself is still preserved (not cleared) in every broken case, for recovery. A deleted target, or one that no longer resolves to a Collection at all, sets `linkBroken: true` and the `markdown` field renders `[collection view: <title or "Deleted collection">]` — a bracketed placeholder in the same spirit as `page_link`'s `[[Title]]`/`[[Deleted page]]`, since a `collection_view` block has no Markdown-native representation of its own.

## 6. What this deliberately leaves open

- **Manual card order.** Persisted `viewConfig` covers filters/sort-mode/visible-properties/grouping-property choice, but Board's per-column manual drag order stays session-local. It's much higher-churn than the rest of the config, and persisting it needs its own design (whose order wins when two people drag concurrently?) — deferred rather than solved by accident.
- **MCP parity.** `query_collection`'s `filter` parameter is still an accepted-but-unused no-op (pre-existing, not introduced by this feature — see `src/lib/mcp/server.ts`), and there is no MCP-facing grouping/sort equivalent to Board/Calendar's. An agent today gets the same unfiltered `rows` regardless of what a human's embedded view is configured to show, and can see that a `collection_view` block exists (via `get_document`) but has no dedicated tool to create or edit one — it can still do so generically via `create_record`/`write_record` with `blockType: 'collection_view'`, since those tools already accept any `BlockType`, but `referencedRecordId`/`viewConfig` on that path aren't validated the way `page_link`'s target is. `query_collection` already reads from the Yjs doc directly, the same source `views.ts` projects over — not the SQLite read model `persistence.md` §2 describes for it, which isn't built (verified against `src/lib/server/db/schema.ts`: no such table exists; see [`mcp-tools.md`](./mcp-tools.md)'s `query_collection` row for the corrected description). Closing the filter/sort gap, formalizing `collection_view` MCP validation, and deciding whether that read model gets built as specced or the direct-Yjs-read approach gets formalized instead, are all tracked separately, not solved here.
- **Board swimlanes.** A second grouping dimension (rows crossing the existing columns) — tracked as a follow-up, not shipped in this cut.
- **Saved/reusable view presets.** Each `collection_view` block's `viewConfig` is that block's own configuration; there's no separate "saved view" a user could apply to multiple embeds or switch between without re-configuring. `data-model.md` §2 no longer describes this as fully undecided (a block's own config is _a_ persistence answer), but a preset/template layer on top remains unbuilt.
