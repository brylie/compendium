# Collection views: Table, Board, Calendar

**Depends on:** [`data-model.md`](./data-model.md) §2 (Collections and views), [`internal-links.md`](./internal-links.md) §1 (`referencedRecordId` resolution), [`service-layer.md`](./service-layer.md)

---

## 1. Scope

This covers the shared view-projection model, the `collection_view` Document block Table/Board/Calendar render through (issue #9), the "smallest shared view configuration" (`EmbeddedViewConfig`) they needed, the draft-vs-saved view state and type-appropriate field summaries issue #32 itself adds (§9) — a deliberately minimal slice of #32's fuller ambition; see §8 for what's still open there. It does **not** cover saved-view persistence beyond what's described in §4/§9, saved/reusable view _presets_ independent of a specific block, or aggregations/charts/dashboards (#10).

**"View" always means a Collection/database view here** — Table, Board, Calendar, and future renderers over one Collection's records — never an MVC-style page or route. There is no standalone view route. A View exists only as `viewConfig` on a `collection_view` block: a Document block, embedded inline like any other (a paragraph, a `page_link`), not a page of its own. The one pre-existing exception is `/table/[id]`, a full-page Table route for a Collection: as of issue #189 it composes `TableCollectionView.svelte` itself (`variant="full-page"`) for its actual grid rather than duplicating it, with only its title/breadcrumb chrome staying route-owned — see §4 and §9.

## 2. `collection_view`: a Document block, not a route

A `collection_view` block is a `WorkspaceRecord` whose `parentId` is a Document, like any other block, with two extra fields (`data-model.md` §1/§2):

- `referencedRecordId` — the target Collection's ID, the same field `page_link`/`synced_block` use for "what this block references." Resolved and permission-checked the same way `page_link`'s target is (`internal-links.md` §1) — see §5 below for the MCP-facing specifics.
- `viewConfig: EmbeddedViewConfig` — `{ viewType: 'table' | 'board' | 'calendar', filters?, sort?, visibleProperties?, groupBy?, swimlaneBy? }`. `filters` is an array of `{ propertyKey, op: 'is' | 'is_not' | 'is_empty' | 'is_not_empty', value? }`, ANDed together. `sort` is `{ mode: 'manual' | 'property', propertyKey?, direction? }` — `'manual'` leaves record order as-is (Board additionally layers a session-local per-column drag order on top, see §3). `visibleProperties` is a property-key allowlist; omitted means "all visible." `groupBy` is the one property driving the layout — a `select` property for Board's columns, a `date` property for Calendar's placement (Table doesn't use it). `swimlaneBy` (issue #67/#165) is Board-only: an optional second `select` property, distinct from `groupBy`, rendering as swimlane rows crossing the existing columns — unused by Table/Calendar, and ignored by Board itself if it ever collides with `groupBy` (see §3/§4).

Both fields are written directly to Yjs from the UI (`setRecordReferencedId`/`setRecordViewConfig`/`patchRecordViewConfig` in `src/lib/data/records.ts`), the same direct-mutation pattern every other block edit uses — not routed through the service layer (`service-layer.md`'s contract is for MCP/route-handler writes; this is human UI editing, audited generically per `audit-coverage.md`, same as a Table schema edit).

**Inserting one:** the slash menu's "Collection view" command (`SlashMenu.svelte`) converts the current block to `collection_view` with no target set. `CollectionViewBlock.svelte` then renders an inline picker — a view-type select and a Collection select, mirroring `page_link`'s unlinked-picker state (`internal-links.md` §2) — and writes both `referencedRecordId` and `viewConfig` together once the user picks both and clicks Insert. A "Change" button on a configured embed reopens the same picker to retarget it.

**Two embeds, one Collection:** two `collection_view` blocks referencing the same Collection with different `viewConfig` are independent — each is its own `WorkspaceRecord` with its own `viewConfig`, so filtering one doesn't affect the other, and both read/write the same underlying records live.

## 3. The shared projection: `src/lib/data/views.ts`

A Collection stays the sole structured-data source of truth (`data-model.md` §2): this module only ever reads `WorkspaceRecord[]`/`PropertyDefinition[]` already loaded from Yjs and returns derived arrays. Nothing here mutates a record, copies one, or adds a view-specific field. `ViewConfig`/`ViewFilter`/`ViewSort`/`EmbeddedViewConfig` are defined in `src/lib/data/types.ts` (re-exported from `views.ts` for existing import sites) — `types.ts` is where `WorkspaceRecord.viewConfig`'s type needs to live regardless, so the view-config shape and the block-storage shape share one definition rather than two that could drift.

- `getCollectionView(doc, collectionId)` — the one Collection query/projection path. `TableCollectionView`/`BoardCollectionView`/`CalendarCollectionView`/`FieldManagerDialog`/`/table/[id]` all read through this (indirectly, via `useCollectionView` below), so a record edit shows up identically in whichever view is open — there's no separate per-view data path to fall out of sync.
- `useCollectionView(getDoc, getCollectionId, onSnapshot?)` (`src/lib/client/collection-view.svelte.ts`, issue #103) — the shared Svelte 5 runes helper wrapping `getCollectionView` with the live-subscription boilerplate every call site above used to duplicate individually: an initial read, `records`/`collections` `observeDeep` subscriptions that re-read on every subsequent mutation, and cleanup when `getDoc()`/`getCollectionId()` change or the caller's own effect is torn down. It exposes `{ schema, rows, primaryFieldKey, collection }` as reactive getters. `getDoc` returning `undefined` (not yet connected, or deliberately inactive — `FieldManagerDialog` only wants this live while its dialog is `open`) tears down any subscription without resetting the last-read snapshot. The optional `onSnapshot` callback runs synchronously right after each internal read, for view-specific logic that needs that exact read — e.g. Board/Calendar's "auto-pick a default groupBy once per connect," or `/table/[id]`'s own title-mirroring.
- `useCollectionConnection(getCollectionId, onReconnect?)` (same file, issue #189) — the shared shard-resolution hook. `TableCollectionView`/`BoardCollectionView`/`CalendarCollectionView`/`/table/[id]` each used to duplicate an identical `$effect` that `fetch`es `/api/collections/[id]/shard` (#120), connects via `getShardDoc`, and guards against a stale response landing after the caller retargeted to a different Collection mid-flight; this hook is that `$effect`, called once per renderer instead. It returns `{ ydoc, shardId, resolvedCollectionId }` as reactive getters — `resolvedCollectionId` is set in lockstep with `ydoc`, never the raw `collectionId` a caller just passed, since `useCollectionView` must never see a doc paired with a collectionId it doesn't belong to. The optional `onReconnect` callback runs synchronously at the start of every (re)connect attempt, before the async fetch, for a caller that needs to reset its own per-connection state (Board/Calendar's "auto-pick a default groupBy once per connect" guard).
- `applyFilters` / `applySort` / `projectRecords` — pure functions composing filters/sort over a records array. `applySort`/`projectRecords` take the Collection's `schema` alongside the records, specifically so a `select`-field sort can look up the sorted property's `options` array (issue #95): a `select` value ranks by its **position in that array** — the same order `groupBySelectProperty` already renders Board columns in — not by its opaque, generated option id (a plain string compare of ids bears no relationship to a configured workflow order like "Backlog → In progress → Done"). An option id no longer present in `options` (deleted, or a schema the caller doesn't have loaded) has no rank and is treated as empty, sorting last regardless of direction — the same bucket `groupBySelectProperty`'s own catch-all "No `<property>`" column already puts it in. This is the one canonical Select-order contract Table/Board/Calendar's sort and Board's column order all share; every other property type's sort comparison (text/number/date/checkbox/relation) is unchanged from before #95.
- `visibleProperties(schema, config)` — the schema filtered down to `config.visibleProperties`, or the full schema when unset.
- `groupBySelectProperty(records, property)` — Board's column grouping. Returns one `BoardColumn` per schema-defined option, **in schema order, even when empty** (data-model.md's "preserve empty groups… do not create placeholder records" — an empty column is a rendering fact about the schema, not a record), plus a trailing catch-all column for records with no value (or an option ID no longer in the schema).
- `groupBySwimlaneAndColumn(records, columnProperty, swimlaneProperty)` (issue #67/#165) — Board's optional second grouping dimension, crossing `swimlaneProperty`'s own options with `columnProperty`'s columns. Returns one `BoardSwimlane` per `swimlaneProperty` option (in schema order, plus a trailing catch-all — same shape as `groupBySelectProperty`'s own option handling), each carrying its own full `groupBySelectProperty(...)` column set computed only over the records in that swimlane — so every column still renders inside every swimlane, including an otherwise-empty one, the same "preserve empty groups" guarantee `groupBySelectProperty` already gives at one dimension, now crossed at two.
- `dateKeyForRecord(record, property)` — the `YYYY-MM-DD` portion of a `date` property's value, or `undefined` if unset. Calendar buckets records by this key; records where it's `undefined` render in an "Unscheduled" list rather than being silently dropped.

This is the entire "smallest shared configuration" issue #9 asked for — it is not `query_collection`'s eventual filter/sort implementation (see §9).

## 4. The three renderers, and their shared editing primitives

Each is a standalone component (`src/lib/components/*CollectionView.svelte`) taking `{ collectionId, config: ViewConfig, onConfigChange }` — no route, no page chrome, no knowledge of being embedded, and no knowledge of draft-vs-saved state either (see §9): a renderer just calls whatever `onConfigChange` it's handed. `CollectionViewBlock.svelte` is the only thing that knows about `collection_view` blocks: it resolves `referencedRecordId`, renders the picker/broken/resolved states, and wires `onConfigChange` to a local draft (§9) rather than a direct Yjs write — a config edit only reaches the embedding block once the viewer clicks Save. This is why `config` is passed as a plain prop with a callback rather than Svelte's `bind:` two-way binding — the value's source of truth is component-owned draft state layered over a Yjs record read, not component-local state alone.

**Shared row/cell/select-option mutation primitives** (`src/lib/client/collection-editor.ts`, issue #189) — `createCollectionRow`, `removeCollectionRow`, `setCollectionCell`, `addCollectionSelectOption`, and `appendCollectionField` are the one implementation every renderer below (plus `FieldManagerDialog`, §6) calls for these operations, each a thin `records.ts`-primitive wrapper handling the "not connected yet" guard uniformly. `addCollectionSelectOption` in particular is the single path to `records.ts`'s validated, deduped, palette-colored `addSelectOption` (§6) — before #189, Calendar and `/table/[id]` each rebuilt the schema by hand instead, silently allowing duplicate, uncolored options that Table and Board's already-canonical path rejected. Renderer-specific behavior (Board's column-value pre-seed, Calendar's date pre-seed) stays in the renderer, layered on top of `createCollectionRow`.

**Table** (`TableCollectionView.svelte`) — a grid over `visibleProperties(schema, config)` columns and `projectRecords(rows, config)` rows, each cell a `PropertyValueCell.svelte` (the same property-type-to-editor mapping every view shares — text/number/date/select/checkbox/relation, one implementation, not reimplemented per view). Each column header carries its own `FieldMenu.svelte` (rename/change type, insert left/right, duplicate, hide in this view, delete — see §7), and `ViewToolbar` exposes a "Manage fields" entry point (`FieldManagerDialog.svelte`) shared by Table, Board, and Calendar alike. It takes a `variant: 'embedded' | 'full-page'` prop (default `'embedded'`): embedded mode shows a small link to `/table/[id]` when the collection has no properties yet (creating the very first field needs a real row/column grid to attach to) and an "Open full table →" footer link; `/table/[id]` itself renders this same component with `variant="full-page"`, which suppresses both (a self-link to the page already showing would be nonsensical) and always renders the grid, even with zero fields, matching the full-page route's pre-#189 behavior. Two callback props, `onConnect`/`onSnapshot`, let a composing parent (only `/table/[id]` today) observe the component's own resolved `Y.Doc` and collection snapshot — e.g. for its own title-editing input — without maintaining a second, redundant `useCollectionConnection`/`useCollectionView` pair alongside the one this component already owns.

**Board** (`BoardCollectionView.svelte`) — `config.groupBy` names the `select` property driving columns; a dropdown lets the user switch it if the schema has more than one, or the collection gets prompted to add one (`appendCollectionField`) if it has none, rather than silently rendering nothing. Cards show the record's first `text`-type property as a directly-editable title, plus whatever other schema properties are in `visibleProperties`. Moving a card between columns — via native HTML5 drag-and-drop, a card's own "Move to" `<select>` (a keyboard/screen-reader-accessible alternative to drag-and-drop), or the card's own field editor if the grouping property is also a visible field — updates that record's existing grouping property (`setCollectionCell`); it is never a reorder of Collection membership or a record copy. Manual sort mode (`config.sort.mode === 'manual'`, the default) additionally supports dragging a card to a specific position within a column — that ordering is **session-local component state** (`manualOrder: Record<columnKey, recordId[]>`), not written to the block or the Collection (see §8 for why manual order specifically stays ephemeral even though the rest of `viewConfig` is now a draft that gets explicitly saved — §9).

**Board swimlanes** (`config.swimlaneBy`, issue #67/#165) — an optional second grouping dimension, rows crossing the existing columns, GitLab/Jira-style. A "Swimlane by" dropdown next to "Group by" offers every `select` property in the schema except whichever one is already `groupBy` (Board never lets one property drive both dimensions); it's hidden entirely when no other `select` property exists, rather than prompting to create one the way the initial "Group by" empty state does — the swimlane dimension is optional, not required to use Board at all. When set, `groupBySwimlaneAndColumn` (§3) replaces the flat column render with one row per swimlane (plus a trailing "No `<property>`" catch-all), each rendering the same full column set — every column still appears inside every swimlane, including an otherwise-empty one, matching `groupBySelectProperty`'s own "preserve empty groups" rule at the second dimension. Both the "Move to column" `<select>` and a parallel "Move to swimlane" `<select>` are per-card, keyboard/screen-reader-accessible alternatives to drag-and-drop; dragging a card into a different swimlane's column cell (or dropping it via native drag-and-drop) sets both the column and swimlane grouping properties in one `setCollectionCell` call, and the swimlane-only move sets just the swimlane property, leaving the record's column untouched. Manual per-cell card order (§8) is scoped by swimlane too, keyed by `` `${groupBy}:${swimlaneBy}:${swimlaneOptionId}:${columnOptionId}` `` — switching either grouping property, or moving a card across swimlanes, never resurrects a stale order saved under a different cell. Retargeting "Group by" onto the property currently driving swimlanes clears `swimlaneBy` (rather than leaving it pointing at what's now the column property too — a duplicate-dimension state `swimlaneCandidates` can never resolve back to) as part of that same `onConfigChange` call; a different retarget leaves `swimlaneBy` untouched. If `swimlaneBy` ever names a property that's been deleted out from under it instead, the swimlane row disappears and Board falls back to its flat single-dimension column view — the same graceful-degradation `groupProperty` itself already has when `groupBy` names a missing field.

**Calendar** (`CalendarCollectionView.svelte`) — `config.groupBy` names the `date` property driving placement, same add-one-if-missing prompt as Board. A fixed 6-row/42-cell month grid (leading/trailing days from adjacent months included, so the grid's shape doesn't jump between 5- and 6-row months) places each record on the day matching `dateKeyForRecord`; a record with no value for the date property renders in an "Unscheduled" section below rather than being hidden. Every entry (scheduled or unscheduled) renders its date property inline via `PropertyValueCell`, so rescheduling — including giving an unscheduled record its first date — is a direct edit. A day cell's "+" button creates a record with that day pre-filled (`createCollectionRow`).

## 5. Permission scoping and `get_document`

`services/documents.ts`'s `getDocument` treats a `collection_view` block's `referencedRecordId` exactly like a `page_link`'s (§ referenced in `internal-links.md` §1): `tokenAllowsParent` is already parent-kind-agnostic (checks a token's `allowedDocumentIds` _or_ `allowedCollectionIds`), so an out-of-scope target is omitted from the response — never leaking the target Collection's title or schema to a caller who was never granted access to it — using the identical `targetInScope` computation `page_link` already had. `viewConfig` is included only once `referencedRecordId` resolves to an in-scope Collection — omitted both when the target is out of scope (it can name properties from a schema the caller isn't scoped to see) and whenever the block is broken (target deleted, or resolves to a Document rather than a Collection), not just the out-of-scope case. `referencedRecordId` itself is still preserved (not cleared) in every broken case, for recovery. A deleted target, or one that no longer resolves to a Collection at all, sets `linkBroken: true` and the `markdown` field renders `[collection view: <title or "Deleted collection">]` — a bracketed placeholder in the same spirit as `page_link`'s `[[Title]]`/`[[Deleted page]]`, since a `collection_view` block has no Markdown-native representation of its own.

## 6. Field management: `FieldMenu` and `FieldManagerDialog`

**Field** is the schema-level term (Collection-wide, in `CollectionMeta.schema`); **column** is Table's own presentation of a field. This distinction matters because field edits — rename, retype, insert, duplicate, delete — are Collection-wide, while a field's _visibility_ in one particular embed is that `collection_view` block's own `viewConfig.visibleProperties`, not schema.

Both new components call `src/lib/data/records.ts` directly against the browser's own `Y.Doc`, the same direct-UI-mutation pattern every other schema edit in this codebase uses (`updateCollectionSchema` from `+page.svelte` predates this feature) — not routed through the service layer, and picked up generically by `attachDocAuditObserver` (`audit-coverage.md`) like any other direct UI write.

- **`FieldMenu.svelte`** — a per-field dropdown (the header's "⋯" button in Table, or a row's own menu inside `FieldManagerDialog`) offering: **Edit field** (one popover form covering both rename and change-type — Airtable folds these together rather than exposing them as two separate top-level actions), **Insert left/right** (a plain `text` field titled "New field", inserted immediately adjacent — no auto-opened rename prompt, kept deliberately simple), **Duplicate** (`duplicateCollectionProperty` — fresh key, "`<label>` copy", every record's existing value copied under the new key), **Hide in this view** (only rendered when the caller passes `onToggleVisible` — i.e. only from an embedded view's own header, never from `FieldManagerDialog`, which has no single view's `visibleProperties` to toggle), and **Delete field** (a `ConfirmDialog` naming how many records currently hold a value, via `countRecordsWithProperty`, before `deleteCollectionProperty` runs).
- **Change-type migration.** `coercePropertyValue` defines the only lossless-enough conversions: number/date/checkbox → text, and a parseable text → number/checkbox. Everything else (anything into/out of `date`/`select`/`relation`) has no generic safe conversion and clears the value. `previewCollectionPropertyTypeChange` counts how many filled records would lose their value under a given target type, shown in the edit form before the user confirms by saving — there's no separate confirmation step beyond that inline warning, since (unlike delete) a retype's data loss is scoped to one field's values, not the field's existence.
- **Delete repair.** `deleteCollectionProperty` does three things in one transaction: drops the field from schema, strips its value off every record that had one, and walks every `collection_view` block referencing that Collection to strip the deleted key out of `filters`/`visibleProperties`/`groupBy`/`sort.propertyKey` — an embed left pointing at a schema key that no longer exists would otherwise silently mis-filter, mis-group, or mis-sort the next time it renders. Manual per-column Board order is untouched (it isn't part of `viewConfig` in the first place — see §7).
- **`FieldManagerDialog.svelte`** — the collection-level "Manage fields" entry point, reachable from `ViewToolbar` — so Table, Board, Calendar, and (since #189, via the composed `TableCollectionView`'s own `ViewToolbar`, §4) `/table/[id]` all share one dialog and one implementation, rather than `/table/[id]` wiring up a second `FieldManagerDialog` instance of its own as it did before. Lists every field in schema order with up/down reorder buttons (a keyboard-accessible alternative to drag, matching Board's own drag/non-drag pattern in §4) — reordering is a plain `updateCollectionSchema` call with the array position swapped, not a new data function — a `FieldMenu` per row, and an "Add field" form at the bottom. It is itself a modal (`role="dialog"`, focus-trapped, closes on Escape), and nests `FieldMenu`'s own `ConfirmDialog` for delete — the reason `ConfirmDialog.svelte`'s Escape/Tab-wrap handling now calls `stopPropagation()` (previously it didn't need to, since no dialog had ever nested inside another one): without it, Escape on the inner delete confirmation would bubble up and close the field manager underneath it too.
- **Select-option lifecycle** (issue #94) lives inside `FieldMenu`'s "Edit field" form, one level below the field-level rename/retype it already did: whenever `property.type === 'select'`, the form additionally renders the field's `options` array as an editable list, backed by five new `src/lib/data/records.ts` functions that mutate one option at a time rather than replacing the whole `options` array by hand the way the pre-#94 "+ add option" affordance did:
  - `addSelectOption(doc, collectionId, propertyKey, label, color?)` appends an option with a fresh `nanoid(6)` id, auto-assigning the next color from `src/lib/data/select-colors.ts`'s fixed nine-color palette when none is given — every add path (the field editor's own "Add option" row, and `PropertyValueCell`'s "+" affordance in Table/Board/Calendar/`/table/[id]`, all via `addCollectionSelectOption` in `src/lib/client/collection-editor.ts`, §4) funnels through this one function, so an option is never colorless and the same blank/duplicate-label rejection applies everywhere, not just the field editor. Calendar and `/table/[id]` bypassed this with a hand-rolled schema rebuild before issue #189 closed that gap.
  - `updateSelectOption(doc, collectionId, propertyKey, optionId, { label?, color? })` renames and/or recolors one option in place.
  - `moveSelectOption(doc, collectionId, propertyKey, optionId, toIndex)` is the single reorder primitive — clamped to the array's bounds — behind both the option list's up/down buttons (keyboard-accessible, matching `FieldManagerDialog`'s own field-reorder pattern) and native HTML5 drag reordering (matching Board's existing card-drag pattern) on the option rows. Since Board's column order (`groupBySelectProperty`), the cell dropdown, and the filter-value dropdown all already iterate `property.options` in array order, this one function is also what reorders all three — no separate ordering field was needed.
  - `countRecordsWithSelectOption(doc, collectionId, propertyKey, optionId)` — the per-option affected-record count shown in a `ConfirmDialog` before delete, mirroring `countRecordsWithProperty`'s field-level equivalent.
  - `deleteSelectOption(doc, collectionId, propertyKey, optionId)` removes the option, clears the value on every record currently set to it (the resulting state is the same "no value" a record already has before ever touching this field — Board's existing catch-all `No <property>` column and the cell dropdown's blank `—` entry, not a new state), and strips any embedded view's `filters` entry that referenced the deleted option by value (a narrower repair than field deletion's: `groupBy`/`sort`/`visibleProperties` name the field itself, which still exists after only one of its options is gone).
  - Add/rename both reject a blank or case-insensitive-duplicate label within the same field (`ValidationError`, surfaced inline rather than thrown past the UI) rather than defining a disambiguation policy — Airtable and Notion do the same.
  - Deliberately not built: a default option for newly-created records. It would need every create path (Table's "+ add row", Board's "+ add card", Calendar's day-cell "+", and MCP's `create_record`) to agree on how to apply it, which is a larger cross-cutting change than one field editor's option list — tracked as a follow-up rather than folded in here.

## 7. Primary field: record title/identity (issue #96)

Board and Calendar cards used to title themselves off "the first `text`-type field in schema order" — implicit, and silently reshuffled by an unrelated field reorder (`FieldManagerDialog`'s own up/down buttons). Issue #96 replaces that with an explicit, Collection-wide **primary field** — Airtable's primary field, GitLab's issue title — the smallest durable model that fits this codebase's existing shape: one field per Collection, not a per-view override, matching `data-model.md` §2's rule that a view "never copies records, changes their identity, or introduces view-specific row fields." A view-specific title would have meant Board and Calendar disagreeing about a record's own name; a single Collection-level choice keeps identity view-agnostic, the same way a record's `id` already is.

- **Storage.** `Collection.primaryFieldKey?: string` (`data-model.md` §1) — a schema key, stored the same whole-value way as `schema` itself (`readCollectionMeta`/`ymeta.set('primaryFieldKey', ...)` in `src/lib/data/records.ts`). Absent on every Collection created before this feature, and on any Collection where no field has been explicitly chosen since — no migration script runs; resolution (next bullet) is what makes an unset Collection keep behaving exactly as it did before.
- **Resolution: `resolvePrimaryField(schema, primaryFieldKey)`.** Returns the schema field named by `primaryFieldKey` when it exists and is an eligible type; otherwise falls back to the first `text` field in schema order — the exact pre-#96 implicit rule — so a Collection created before this feature, or one whose chosen primary field was since deleted or retyped away, keeps showing the same title without a migration step. The fallback only ever considers `text` fields, not every eligible type, so this returns `undefined` both when the schema has no eligible field at all and when it has eligible fields (e.g. a lone `number` or `select` field) but none of type `text` (Board/Calendar's card/entry title then reads "Untitled", same as before). Board and Calendar both call this in place of their old `schema.find(p => p.type === 'text')` line; `FieldMenu`'s primary-field indicator (next bullet) calls it too, so the star always matches what's actually titling a card.
- **Eligible types: everything except `relation`.** A `relation` value is a list of record IDs with no display string of its own (data-model.md's `PropertyValue`) — every other type (`text`, `number`, `date`, `select`, `checkbox`) already renders as one displayable value via `PropertyValueCell`, so `setPrimaryField` rejects choosing a `relation` field (`ValidationError`), and a retype that turns the current primary field _into_ `relation` clears `primaryFieldKey` in the same transaction rather than leaving it pointing at a now-invalid field. Deleting the current primary field clears it the same way. Both repairs mirror the existing `deleteCollectionProperty`/`updateCollectionProperty` pattern of fixing up stale schema references in one transaction rather than leaving a dangling key for a reader to notice later.
- **Display value: `primaryFieldDisplayValue(value, property)`** (`src/lib/data/views.ts`) — a plain-text rendering of any eligible type's value (a `select` value resolves through `property.options` to its label; `checkbox` renders "Checked"/empty), used for Board/Calendar's card-title `aria-label`s and Calendar's static entry-title text. Board's own card _editor_ still renders the primary field as a full `PropertyValueCell` (so whichever type is chosen — not just `text` — stays directly editable inline); this function is only for the places a plain string is needed instead of an editable cell.
- **Control and indicator: `FieldMenu`.** A "Set as primary field" / "Unset primary field" menu item (disabled, with an explanatory `title`, for a `relation` field) calls `setPrimaryField`/`setPrimaryField(..., null)` directly — the same direct-Yjs-mutation pattern every other `FieldMenu` action already uses. The toggle's own `isPrimary` state compares the Collection's raw `primaryFieldKey` prop against `property.key` directly — deliberately **not** through `resolvePrimaryField` — because a resolved comparison would make the auto-fallback field's own toggle a permanent no-op: with `primaryFieldKey` unset, the fallback field already resolves as primary, so a resolved `isPrimary` would read `true` and the menu would only ever offer "Unset," writing `null` onto an already-`null` key with no way to actually promote that field to an explicit choice. The small star indicator next to a field's label (rendered by each of `FieldMenu`'s call sites — `TableCollectionView` and `FieldManagerDialog`; `/table/[id]` inherits it by composing `TableCollectionView` (§4) rather than rendering its own `FieldMenu` any more; Board/Calendar show no column headers, so neither renders `FieldMenu` at all) is unaffected by this distinction: those call `resolvePrimaryField` themselves for display, so the star still reflects the _resolved_ primary field, including the auto-fallback case, even while the field's own toggle correctly reads as "not yet explicitly set."
- **MCP-visible schema.** `collections.listCollections` and `collections.queryCollection` (`mcp-tools.md`) both include a `primaryFieldKey` alongside `schema` in their response — the _resolved_ key (`resolvePrimaryField`'s result), not the raw possibly-unset stored value, so an agent always sees which field is actually titling a record right now rather than having to reimplement the fallback rule itself.
- **Deliberately not built.** A per-view override (a Board embed titling its cards differently than a Table view of the same Collection) — data-model.md §2's "a view never introduces view-specific row fields" argues directly against it, and no user story in this repo has asked for cards and rows to disagree about a record's name. Record templates, formula/computed primary fields, and multi-field display identities (e.g. "first + last name") are out of scope for the same reason #96 itself lists them as non-goals — they're a different, larger feature than "pick which existing field is the title."

## 9. Draft view state, explicit save, and field summaries (issue #32)

**The problem this closes.** Every `ViewToolbar` edit — adding a filter, changing sort, toggling a visible property, switching Board/Calendar's grouping property — used to call `onConfigChange` straight through to `setRecordViewConfig`, writing the shared `WorkspaceRecord.viewConfig` field on every interaction. Two collaborators (two browser tabs, a human plus their own connected AI client, or two people once Phase 1 auth exists — see `docs/prd.md`'s Phase 0/1 split) viewing the same `collection_view` embed would see each other's in-progress, not-yet-decided filter edits live. Per the issue's own sharpened acceptance criterion: _"given two collaborators apply temporary filters/search to the same Collection, neither changes the other's current view; saving a view makes its scope explicit."_

**The fix: `CollectionViewBlock.svelte` owns a draft/saved split, not the renderers.** `TableCollectionView`/`BoardCollectionView`/`CalendarCollectionView` and `ViewToolbar` are unchanged — they still just call whatever `onConfigChange` they're handed. `CollectionViewBlock` now holds two values instead of passing `block.viewConfig` straight through:

- `persistedConfig` — `block.viewConfig`, i.e. what's actually shared and visible to every other connection.
- `draftConfig` (`$state`) — what this viewer's own toolbar edits mutate, via a wrapped `onDraftChange` passed to the three renderers instead of a direct write. An explicit `isDirty` flag (`$state`, not a derived comparison — see below) drives an "Unsaved changes" indicator plus **Save view**/**Discard** buttons next to the existing **Change** button.
  - **Save view** diffs `draftConfig` against the config this draft was last synced from (`views.ts`'s `diffViewConfig`) and calls `patchRecordViewConfig` with only the members that actually changed — the one and only point this feature writes to the shared record — then clears `isDirty` immediately. It's a patch rather than a whole-value `setRecordViewConfig` write specifically so that a stale copy of a member this viewer didn't touch (e.g. `sort`, while they only meant to change `filters`) can't overwrite another actor's concurrent Save of that member — see data-model.md §4's `viewConfig` merge-granularity note (issue #71).
  - **Discard** resets `draftConfig` back to `persistedConfig` and clears `isDirty`, touching Yjs not at all.
  - Retargeting to a different Collection (`insert()`'s existing flow) always resets the draft — a brand new embed target has no prior draft to preserve.
  - An external Save from another connection (another tab, another client) is picked up automatically — `draftConfig` re-syncs to the new `persistedConfig` — **only when `isDirty` is false**. A viewer with their own unsaved edits never has them silently clobbered by someone else's concurrent Save; the two saves simply don't race, because nothing but an explicit local Save ever writes.
  - `isDirty` is deliberately its own flag (set `true` by every `onDraftChange`, cleared by Save/Discard) rather than a live `draftConfig`-vs-`persistedConfig` equality check: the latter would depend on the parent's own `block` prop re-rendering once Yjs's observer round-trips this viewer's own write, which is real but not synchronous — this viewer's own Save/Discard should stop showing "Unsaved changes" the instant they click it, not once a prop happens to catch up. `viewConfigsEqual` (`src/lib/data/views.ts`) still exists and is used, but only for structural comparisons that don't need to be instantaneous.
- This is a **per-connection, ephemeral** distinction, not a per-user one — Phase 0 has no login/authentication (`docs/prd.md` Non-Goal #7), so there is no persisted "my personal view" anywhere. A draft lives only in this component instance's memory for as long as the tab/connection is open; closing the tab without saving discards it, same as any other unsaved form. This is **not** the PRD's Nice-to-Have "Saved, shareable view configuration" (a named, addressable artifact reusable across embeds, still unbuilt) — it only changes _when_ an edit to the one config a `collection_view` block already has gets promoted from local to shared.
- `/table/[id]` (per §1/§4, since issue #189) composes `TableCollectionView` directly and so now does have a `ViewToolbar`/`ViewConfig` surface — filters, sort, visible fields, field summaries — same as an embedded Table. It has no `collection_view` block of its own to persist a config onto, so unlike §9's draft/save flow, this route's `config` is a single ordinary `$state<ViewConfig>({})` local to the page: there is no draft/persisted split, no Save/Discard, and no cross-connection sharing to worry about — a filter chosen here is this browser tab's own, resetting on reload, same as it would for any unsaved local UI state.

**Field summaries.** `ViewConfig.summaries?: Record<string, FieldSummaryType>` (`src/lib/data/types.ts`) — Table only renders a `<tfoot>` row with one type-appropriate aggregation picker per visible column (a `<select>`, defaulting to `none`), mirroring Notion/Airtable's column-footer summary. `summaryOptionsForType(propertyType)` and `computeFieldSummary(records, property, type)` (`src/lib/data/views.ts`) are pure functions: `text`/`select`/`relation` offer only the generic `count_all`/`count_values`/`count_empty`; `number` adds `sum`/`average`/`min`/`max`; `date` adds `earliest`/`latest`; `checkbox` offers `checked`/`unchecked`. A summary is computed over Table's already-filtered/sorted `projected` rows, not the Collection's raw rows, matching the convention every other Notion/Airtable-style footer aggregation uses (a summary reflects what's currently visible). Choosing a summary is itself a `ViewConfig` edit — it goes through the same draft/Save flow as filters/sort/grouping above, not a separate always-shared setting. Board and Calendar don't get a footer; there's no natural per-column place to put one in either layout, and neither view's card/entry grid already renders columns the way Table's grid does.

**MCP query semantics vs. UI view semantics.** These stay two separate surfaces by design, not because of an oversight: `query_collection` (`mcp-tools.md`) reads a Collection's raw records — the same `WorkspaceRecord[]`/`PropertyDefinition[]` `getCollectionView` loads — with **no** filter/sort/grouping/summary applied server-side; its `filter` parameter remains an accepted-but-unused no-op (§8 below), and there's no `sort`/`groupBy`/`summaries` parameter at all. A UI `ViewConfig` (draft or saved) is purely a rendering/projection choice `views.ts`'s pure functions apply client-side over that same raw data — it is never a data-access restriction, and an agent calling `query_collection` today is never implicitly scoped by whatever a human's embedded view happens to be filtered to. This is the intentional halves of one design: `applyFilters`/`applySort`/`projectRecords`/`groupBySelectProperty`/`computeFieldSummary` are all already agent-callable in principle (they're plain exported functions over data an agent can already fetch via `query_collection`+`get_document`'s `viewConfig`), so closing the parity gap (giving `query_collection` real filter/sort parameters) is additive engineering work, not a semantics question this section leaves open. See §8's MCP-parity item for what's still unbuilt there.

## 10. Relation property: target Collection, picker, and broken-target rendering (issue #15)

`PropertyValue`'s `relation` variant (`{type: 'relation', value: string[]}`, `data-model.md` §1) predates this section — issue #15 is what makes it actually usable: a schema-level target, a search-to-select picker in place of the former raw comma-separated-id `<input>`, and graceful rendering when a referenced record is deleted.

- **`PropertyDefinition.targetCollectionId?: string`** (`data-model.md` §1) — which Collection a relation field's record-id values point into. Unconstrained before this issue (no field named it at all); now set once, when the field is created or retyped to `relation`, via a "Target collection" `<select>` that appears in both `FieldManagerDialog`'s "Add field" form and `FieldMenu`'s "Edit field" form, populated from a `collections: CollectionMeta[]` prop threaded down from the root layout's catalog-backed list (the same list `CollectionViewBlock`/`Sidebar` already use, not a live Yjs read — picking a target Collection isn't itself something that needs to be live). `updateCollectionProperty`'s patch gained a matching `targetCollectionId?: string | null` — `null` clears it, an explicit value sets it, and it's dropped automatically on any retype away from `relation`, the same "irrelevant to this type" cleanup `options` already gets on a retype away from `select`.
- **The picker: `RelationPropertyCell.svelte`**, swapped in for `PropertyValueCell`'s old `relation` branch (the raw `input.split(',')` id-list editor) with no change to `PropertyValueCell`'s own per-type dispatch — Table/Board/Calendar keep routing every relation cell through `PropertyValueCell` uniformly, per §4's "one implementation, not reimplemented per view." It resolves and connects to the target Collection's own shard via a new `resolveCollectionDoc(collectionId)` (`src/lib/client/yjs-client.ts`, memoized per Collection id for the tab's lifetime) — almost always a _different_ shard than whichever Collection owns the relation field itself, unlike every other property type's cell, which only ever reads the row's own Collection. Once connected, `useCollectionView` (`src/lib/client/collection-view.svelte.ts`, the same shared hook `FieldManagerDialog`/Table/Board/Calendar already use) gives it the target's live `schema`/`rows`; `resolvePrimaryField`/`primaryFieldDisplayValue` (§7) resolve each selected id to a display title. Selecting a candidate from the search list, or removing a chip, calls `oninput` with the updated `string[]` — the same `PropertyValue`-in/`PropertyValue`-out contract every other cell type already has; no new record-level data function was needed for reads or writes themselves, only for target-Collection resolution.
- **A relation pointing at a deleted record** renders as a distinct, visually broken chip (dashed border, warning icon, the raw id as its label) rather than a blank or silently-dropped value — the id is preserved, never cleared automatically. This is the same precedent `internal-links.md` §2 already established for a `page_link` pointing at a deleted Document: broken is its own state, not indistinguishable from "empty" or "still valid," and deleting a target never cascades an edit onto every record that references it (`internal-links.md` §3) — a relation value stays exactly as broken-but-present until a human or agent explicitly removes it.
- **No target Collection configured** (a relation field created before this issue, or one nobody has set a target for yet) renders existing values as plain, unstyled ids with a "No target collection set" note in place of the search picker — there's nothing to search against, but existing data still isn't hidden or dropped. If the configured `targetCollectionId` no longer resolves to a real Collection (deleted), the cell instead shows "Target collection not found," the same "don't hide existing data, but be honest that something's wrong" posture.
- **MCP `write_record`/`create_record`** already accept a `relation` property value generically — `propertyValueSchema`'s `relation` branch (`src/lib/mcp/server.ts`) matches `PropertyValue`'s `relation` variant exactly, with no special-casing, so an agent could already set relation values with zero server changes. `targetCollectionId` flows through automatically too: `list_collections`/`query_collection` return each Collection's whole `schema` array as-is (`mcp-tools.md`), not a hand-picked subset of `PropertyDefinition` fields, so an agent sees `targetCollectionId` the same way a human's picker does — no MCP schema change was needed for either read or write. Creating or retargeting a relation _field_ (as opposed to setting a relation _value_) stays UI-only, consistent with every other field-management action (§6) — there is no MCP tool for schema editing at all yet.

## 8. What this deliberately leaves open

- **Manual card order.** Persisted `viewConfig` covers filters/sort-mode/visible-properties/grouping-property choice, but Board's per-column manual drag order stays session-local. It's much higher-churn than the rest of the config, and persisting it needs its own design (whose order wins when two people drag concurrently?) — deferred rather than solved by accident. (This is a different, finer-grained kind of "local until decided" state than §9's draft `ViewConfig` — manual order was never planned to become part of `ViewConfig` at all, even once saved.)
- **MCP parity.** `query_collection`'s `filter` parameter is still an accepted-but-unused no-op (pre-existing, not introduced by this feature — see `src/lib/mcp/server.ts`), and there is no MCP-facing grouping/sort/summary equivalent to Board/Calendar/Table's — see §9 for why this is a deliberate two-surface design, not an oversight, and what closing it would mean. An agent today gets the same unfiltered `rows` regardless of what a human's embedded view is configured to show. Creating/configuring a `collection_view` block itself is now a validated MCP write path (issue #37, closed): `create_record`'s `blockType: 'collection_view'` is in the MCP schema, its `referencedRecordId` is validated the same way `page_link`'s is (must resolve to an existing, caller-accessible **Collection** — the generic "not an accessible Collection" error, never distinguishing "doesn't exist" from "out of scope"), and both `create_record` and `write_record` accept a `viewConfig` (a whole `EmbeddedViewConfig`, `viewType` required) to configure or reconfigure the embed in the same call — see [`mcp-tools.md`](./mcp-tools.md)'s `create_record`/`write_record` rows. `write_record` additionally accepts a per-member `viewConfigPatch` (issue #195, resolved) on an already-configured embed — the MCP-facing counterpart to this section's `patchRecordViewConfig`, so an agent editing just `filters` or `sort` doesn't have to round-trip `get_document` first and resupply every other member via a whole-value `viewConfig` write, silently clobbering whatever a concurrent human Save or agent call set on a member it never meant to touch. `query_collection` already reads from the Yjs doc directly, the same source `views.ts` projects over — not the SQLite read model `persistence.md` §2 describes for it, which isn't built (verified against `src/lib/server/db/schema.ts`: no such table exists; see [`mcp-tools.md`](./mcp-tools.md)'s `query_collection` row for the corrected description). Closing the filter/sort gap and deciding whether that read model gets built as specced or the direct-Yjs-read approach gets formalized instead are tracked separately, not solved here.
- **Relation search is client-side and unindexed** (§10, issue #15): `RelationPropertyCell`'s picker substring-matches over the target Collection's already-loaded live `rows` (capped at 20 results), not a server-side/full-text search — fine at Phase 0's single-workspace scale, but a target Collection with many thousands of records would need real search before this stays usable. A relation field also has exactly one target Collection; a value that could point into any of several Collections (a polymorphic relation) isn't modeled and isn't asked for by any current user story.
- **Saved/reusable view presets.** Each `collection_view` block's `viewConfig` is that block's own configuration; there's no separate "saved view" a user could apply to multiple embeds or switch between without re-configuring, and no per-user "personal view" persists beyond the ephemeral draft state §9 adds. `data-model.md` §2 no longer describes this as fully undecided (a block's own config is _a_ persistence answer), but the named/addressable/shareable preset layer `docs/prd.md`'s Nice-to-Have "Saved, shareable view configuration" describes remains unbuilt.
