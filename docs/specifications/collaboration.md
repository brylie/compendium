# Presence and holds

**Depends on:** [`data-model.md`](./data-model.md) §2 (Yjs mapping)

---

Built on Yjs Awareness, not a custom channel. Yjs ships an **Awareness** protocol specifically for ephemeral, per-client state that isn't part of document content: cursor position, online status, and similar — it doesn't get persisted or CRDT-merged, and it auto-clears when a client disconnects. That's exactly the shape the PRD's hold mechanism needs, so holds are built on it rather than as a separate custom protocol:

- Each connected client (browser tab or MCP session) publishes an Awareness state: `{ actor: ActorId, heldRecordIds: string[] }`.
- **Human cursor presence → implicit hold:** the browser UI updates its own Awareness state's `heldRecordIds` to `[currentBlockId]` whenever the cursor moves, debounced ~1.5s on move-away (per PRD).
- **Agent hold request:** the MCP server's `hold_records` tool handler checks the _aggregate_ Awareness state across all connected clients for each requested record ID. A record already present in another client's `heldRecordIds` is denied for this request; everything else is granted. This directly implements the PRD's per-record (not all-or-nothing) acceptance criterion. Accurate for Phase 0's single global `Y.Doc`/Awareness pair; [`workspace-sharding.md`](./workspace-sharding.md) (#112, approved) moves Awareness to be shard-local once #113 lands, with a separate workspace-scoped hold coordinator (§3.3) aggregating across shards for a cross-document agent batch — the per-record semantics above don't change, only where the aggregation happens.
- **TTL:** two distinct timeouts are involved, not one:
  - y-protocols' own Awareness implementation clears any client's state after **30s** of no heartbeat (`outdatedTimeout`) — this is what catches an abruptly-dropped connection (e.g. a browser tab closing without a clean disconnect).
  - Agent holds additionally carry a dedicated **100s** `AGENT_HOLD_TTL_MS` timer (`src/lib/server/holds.ts`), scheduled server-side whenever a hold is granted or renewed, sitting inside the PRD's 90–120s auto-release target. This is what auto-releases a hold an agent forgot to explicitly release even while its underlying connection/token is still otherwise alive — the 30s Awareness timeout alone wouldn't cover that case, since a stateless MCP agent has no persistent heartbeat to time out in the first place.
  - A clean WebSocket disconnect (a real browser tab) additionally clears that connection's own Awareness clients immediately, rather than waiting out either timeout — see `src/lib/server/yjs-ws-server.ts`'s close handler.
- **Placeholder rendering:** the UI subscribes to the aggregate Awareness state; any record ID held by an agent renders as the shimmer placeholder with that agent's avatar, sourced directly from the Awareness entry's `actor` field. The placeholder is `role="group"`/`aria-label`-described for a screen reader browsing to it, not a live region itself — see below for how the transition gets announced.
- **Screen-reader announcements:** a hold/release transition is otherwise silent to assistive tech (the shimmer + avatar convey it visually only), so the Document page keeps one persistent, visually-hidden `aria-live="polite"`/`role="status"` region and updates its text on every transition it observes in the diff between the previous and current Awareness snapshot: an actor newly present announces "started editing a block", one no longer present announces "finished editing a block", and one record id whose actor identity changed (a silent handoff, not a departure) announces both halves. The very first snapshot a client receives on connect is not diffed against anything — it seeds state without announcing, since actors already editing before this client joined aren't a transition it observed. Two consecutive transitions that happen to produce identical wording are still distinguished (an alternating invisible marker forces the live region's text to actually change, since a screen reader only re-announces on a real text change) so a live region doesn't go silent on a repeat.

## Collection views: announcing remote content changes (issue #167)

Table/Board/Calendar have no Awareness-based hold state to diff (Collection rows aren't held the way Document blocks are), but a row/card/event a remote actor adds, edits, removes, or repositions while the view is open is exactly as silent to assistive tech as an un-announced hold would be — so they reuse the same live-region pattern PR #159 established above, applied to a different diff source: `useRemoteUpdateAnnouncer` (`src/lib/client/collection-announcer.svelte.ts`) diffs the previous vs. current **Yjs record content** snapshot (`useCollectionView`'s own `onSnapshot`) instead of Awareness, since Collection rows have no ephemeral presence signal of their own. This is the one shared helper behind all three views' live regions, not three independent implementations:

- **"Remote" is per-record, not per-connection:** every `WorkspaceRecord` already carries `createdBy`/`lastEditedBy: ActorId` (see [`data-model.md`](./data-model.md)); a record whose `createdBy` (on add) or `lastEditedBy` (on edit) differs from `CURRENT_USER` (Phase 0's single fixed local identity, [`src/lib/client/actor.ts`](../../src/lib/client/actor.ts)) is remote, the content-diff equivalent of PR #159's Awareness-derived "held by others" filter.
- **Removal has no actor to read** — a deleted record simply isn't in the next snapshot, unlike a released hold (which still names who released it). A view's own delete handler calls `announcer.noteLocalRemoval(id)` immediately before removing its own row/card/event, so the diff can tell "I just deleted this" apart from "someone else deleted this out from under me"; only the latter announces, and unattributed ("A row was removed") since no actor survives to name.
- **View-specific detail, one shared "what changed" hook:** each view supplies an optional `describeEdit(previous, current)` callback so a same-record edit can announce something more specific than the generic "edited a row/card/event" — Board's callback compares the `groupBy` property's value to announce "moved a card to `<column>`", Calendar's compares the date property to announce "rescheduled an event to `<date>`". Table has no `describeEdit` (a generic "edited a row" is the least-noisy signal for arbitrary field-level changes, per the issue's "scoped to what's reasonably detectable without being noisy").
- Same suppression/toggle mechanics as the Document editor: the first snapshot after connect (or after retargeting to a different Collection) seeds state without announcing, and an alternating zero-width-space marker forces a real text change so two consecutive identically-worded announcements aren't silently swallowed.
